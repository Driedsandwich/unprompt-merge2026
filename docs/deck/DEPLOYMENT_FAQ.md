# DEPLOYMENT_FAQ — 展開性・審査員想定問答

目的: 審査員が突く可能性の高い「これはあなたのマシンでしか動かないのでは」系の質問に、誠実かつ具体的に答える。
表記規約: 各回答は **事実**(現状の実装・実測で確認できること)と **構想**(未実装の設計方針・意思決定)を明示的に分けて記す。事実と構想を混在させて断定しない。

---

## Q1. これは開発者本人のマシンでしか動かないのでは? 他者への展開はどうするのか?

**事実**:
- 主経路は Claude Code サブスクリプションの headless CLI(`claude -p`)をローカルプロセスとして呼ぶ構成。Anthropic APIキーは不使用。
- Claude Code にログイン済みの環境であれば、`git clone` + 起動コマンド1つ(`python3 server.py`)で誰でも同一の挙動を再現できる。ビルドレス・サーバレス(npm/Node/バンドラ不使用、バニラJS+Python標準ライブラリ)。
- 現状は「開発者本人のマシン」限定ではなく、「Claude Code サブスクリプションを持つ任意のマシン」で動く状態。ただし他者環境での実機検証はDay3時点では未実施(要検証事項として開示)。

**構想(展開の3形態、優先度順ではなく選択肢として並記)**:
- (a) **ローカル配布**: 利用者各自が `git clone` してローカルで実行。認証は各自の Claude Code ログイン(サブスク)。実行コストは各自のサブスク範囲内で負担。運営側の追加コストはゼロ。
- (b) **ホスティング**: 運営者がサーバを立て、URLで公開。バックエンドは運営者の Anthropic APIキーで `claude -p` またはAPI直叩きを実行。この場合、実行コストは運営者が負担するため、レート制御(1ユーザーあたりの実行回数上限)と利用上限(日次/月次の総枠)の実装が前提条件になる。未実装。
- (c) **BYOK(Bring Your Own Key)**: 利用者がブラウザ側で自分のAPIキーを入力・保持し、その場でAPIを直叩きする経路。ローカルストレージ保持を想定。既に「APIキー保有者向けの代替経路(ブラウザ直叩き)」としてコードパス自体は存置されている(開示リスト#1参照)が、UI上の鍵入力導線・キー管理は未整備。

## Q2. URLで公開したとき、実行コストは誰が払うのか?

**事実**:
- 現状はURL公開・ホスティングを行っていない。コスト負担の主体は「各自のローカル実行」を前提にすれば利用者自身(Claude Code サブスク費用の範囲内)。
- 1セッションあたりのAPI呼び出し構成は実測ベースで把握済み: 判断点抽出1回 + 見本(帰結レンダ)最大15件 + 根拠文生成1回。

**構想**:
- (b)ホスティング・(c)BYOK 選択時のコスト帰属は Q1 の整理と同一。
- 概算実費(Anthropic API単価ベースの粗い見積り、実測ではなく試算): 1セッション(抽出1+見本〜15+根拠文1)でAPI実費は数円〜十数円程度と見込む。これは公開前提でのホスティング判断(レート制御・利用上限の要否)の判断材料であり、確定値ではない。
- ホスティング形態を取る場合、レート制御・利用上限は「あれば望ましい」ではなく、コスト青天井を避けるための必須実装と位置づける。

## Q3. 利用者のデータはどこへ行くのか?

**事実**:
- 現状の経路: 利用者のローカル環境 → Anthropic API のみ。運営者サーバや第三者サーバは経由しない(主経路がローカル実行のため)。
- 実行ログ(判断点・レイテンシ等)はローカルに保存される(EVIDENCE/ 配下等)。外部送信・外部保存は行っていない。
- 入力データの学習利用有無は Anthropic 社のAPI利用ポリシーに準拠する(本プロジェクト側で独自の学習利用は行っていない/行いようがない構成)。

**構想**:
- Q1(b)ホスティング形態を取った場合は、利用者データが運営者サーバを経由する構成になる。この場合はサーバ側のログ保持方針・保持期間・第三者提供有無を明示する設計が必要(未設計)。公開時はこの経由の事実を利用者に明示することを前提条件とする。

## Q4. 各自がダウンロードした場合の認証はどうするのか?

**事実**:
- 認証経路は2通り: ① Claude Code ログイン(サブスク、APIキー不要) ② Anthropic APIキーを環境変数等で渡す代替経路(ブラウザ直叩き、開示リスト#1)。
- 主経路である①の利点は「APIキーの発行・管理・漏洩リスクなしに動かせる」こと。利用者がすでにClaude Codeサブスクを持っていれば、追加の認証設定なしにログイン状態を共有して動く。

**構想**: 特になし(Q1のローカル配布(a)がこの回答とほぼ同義)。

## Q5. Claude専用なのか? OpenAIや他社、ローカルLLMは使えないのか?

**事実**:
- 現状の実装は Claude CLI(`claude -p`)への依存を `ClaudeRunner` という1クラスに局所化している(server.py)。他のモジュールはこのクラス経由でのみモデル呼び出しを行う設計。
- モデルとの契約(インターフェース)は「システムプロンプト + 本文入力 → 構造化JSON出力」のみで、Claude固有の機能に強く依存した設計にはなっていない。
- 実測で品質確認が取れているのは Claude 系のみ(製品エンジンは Sonnet 5 を主とし、初期には Haiku 4.5 も比較実測)。他社モデルでの実測は未実施。

**構想**:
- 契約が「システムプロンプト+本文→構造化JSON」に限定されているため、構造上は OpenAI CLI/API・ollama等のローカルLLMアダプタを `ClaudeRunner` 相当のクラスとして追加し、差し替え可能にすることは可能と考えられる(設計上の可能性であり、実装・検証は未着手)。
- 誠実な留保: 判断点抽出・帰結分岐の質はモデル依存の要素が大きく、他モデルでの抽出精度・再現性は未検証。「構造上は差し替え可能」と「他モデルでも同じ品質が出る」は別の主張であり、後者は現時点で保証しない。

## 使用時の原則(審査員対応メモ)

- 聞かれていない限りQ1〜Q5を先回りで全部説明しない。聞かれた質問にだけ、事実と構想を分けて簡潔に答える。
- 「構想」を「実装済み」であるかのように語らない。特にQ2の金額試算は概算であり、実測コスト計測(EVIDENCE/配下の既存ログ)とは性質が異なる数値であることを都度明示する。
- Q5で「Claude以外でも動く」という趣旨の質問が出た場合、「構造上は可能」までに留め、「他モデルでも同品質」とは言わない。
