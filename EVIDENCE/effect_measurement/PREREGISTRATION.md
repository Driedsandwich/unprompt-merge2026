# 指示書効果測定 — 事前登録 (Brief Effect Measurement)

状態: **ドラフト (ブリーフ10本の確定待ち)**。確定時にこのファイルをローカルコミットして固定し、以後は追記のみ (結果を見てからの設計変更・ブリーフ差し替えを構造的に不可能にする)。Wave 1 審査期間中は push しない (提出物凍結)。公開は Wave 2 開始 (2026-08-10 23:59 JST) 以降。

## 命題

同一の曖昧な一文について、下流のAI制作者に

- **A**: 一文だけを渡す
- **B**: 同じ一文を Unprompt に通して発注者本人が〈決める/委ねる〉した**手渡しJSON** (`unprompt.compiled_brief.v0`) を渡す

とき、B の成果物の方が**発注者本人の意図に近い**。

## 手続き

1. **ブリーフ確定**: 下記候補12本から発注者 (=ユーザー本人) が10本を選定・自由に編集 (自作差し替え可)。確定した10本をこのファイルに焼き付けてローカルコミット (事前登録タイムスタンプ)。
2. **選択セッション**: 発注者が実アプリ (QA常駐 127.0.0.1:8512) で1本ずつ通常フローを実行 (爆散→本人の意図で決める/委ねる→指示書)。「指示書をコピーしてAIに渡す」で得たJSONを `sessions/<id>/handoff.json` に保存。一文は `sessions/<id>/brief.txt`。
   - 選択は本人の実意図で行う (演出のための対照的選択はしない — 既存デモペアとの違い)。
   - 委ねる判断も本人の実感覚で可 (委任も製品の正規の出力)。
3. **生成**: `effect_measure.py` が各ブリーフについて A/B を生成。公平条件は既存並置ペアの拘束を継承: 同一モデル (sonnet)・同一 effort (low)・同一の制作者 system 骨格+デザイン憲章 (`prompts/downstream_maker_v1.txt`)。違いは user prompt (Aは一文 / BはJSON) と、B側のみのコンパイル済みブリーフ取扱2項 (既存ペアと同一の非対称・manifest に全文開示)。A/B とも同一試行回数規則 (HTML不成立時のみ最大2回、記録を残す)。
4. **ブラインド判定 (主指標)**: `eval_blind.html` が10ペアを**ブリーフごとに決定論シャッフルした左右順**で提示 (条件ラベル非表示)。発注者は各ペアについて「自分の意図に近いのはどちらか」(強制二択)+確信度 (1-5) を回答。回答完了までA/Bの対応は開示しない。
5. **副指標**: 各ペアについて、handoff.json の決定事項が成果物に反映されているかのチェックリスト照合 (決定ごとに 反映/部分/なし。機械補助+人裁定・裁定理由を記録)。
6. **第三者判定 (統制)**: 独立エージェント3体が同じブラインド提示で判定 (発注者バイアスの統制)。

## 報告規律

- **n=10・発注者1名の実測**であり、統計的一般化は主張しない。効果の言明は「この10本・この発注者での実測」に限定する。
- **全ペア・全判定・負けたペアを含む生データを公開** (EVIDENCE/effect_measurement/)。選り好みをしない。
- 事前登録後の手続き変更は、変更理由ごと追記で開示する。

## 結果1 (2026-07-31・AI発注者版 v1 の実測 — 事前登録どおり全公開)

- 発注者判定 (主指標): **compiled 2/10・raw 8/10 — 仮説と逆**
- 第三者判定1 (一文のみ): compiled 8/10
- 第三者判定2 (修正往復視点): compiled 5/10
- 生データ: judgments/ (3判定の全文)・decoded_tally.json。復号バグは実ファイル検証で否定 (compiled側のみ選択マーカーとトークン実装を確認)。

### 原因分析 (実ファイルに基づく)

発注者役の選択は**ラベル文字列のみ**を見て行われた (本測定v1の手続きはサムネイル見本を提示していない)。ラベル水準では意図メモと整合する選択 (例: m05「ミニマル徹底」「デザイナー向け」) でも、レンダ工程が生成した視覚トークンは黒地×赤 (#0d0d0d/#ff3b1d) 等となり、メモの美的意図 (「白ベースに文字と余白」) と衝突。compiled側はトークンを忠実に実装するため、その衝突が成果物に固定された。rawは指定がない分、無難な出力がメモに近づいたケースが多い。

**これは製品の中核テーゼ「ラベル (言葉) だけでは意図は選べない — だから見本 (帰結) を見て選ぶ」の定量的な裏付けが、測定手続きの欠陥として現れたものである。** v1の手続きは製品の最重要機能 (見本を見てから決める) を省略しており、製品の実UI体験の測定になっていない。

## 追補2 (設計修正案・実行前に記録): v2 = 見本つき選択

- 発注者判定 (主指標): **compiled 4/10** (v1: 2/10 — 見本提示で改善したが逆転には至らず)
- 第三者判定1: compiled 4/10 (v1: 8/10) / 第三者判定2: compiled 2/10 (v1: 5/10)

### 総合解釈 (事前登録した予測との突合)

予測「見本つき選択で compiled の発注者判定勝率が改善する」は**方向としては成立 (2→4) したが、仮説の主命題 (Bの方が意図に近い) は本測定条件では実証されなかった**。判定理由の全文から特定できた構造的原因:

1. **決定の過剰な文面化**: compiled側の制作者が、決定ラベルを成果物の文面にそのまま露出させる (例:「実務2〜4年目って」をメール本文に書く、「かっこよさ/信頼感」を見出しに直訳)。判定者はこれを不自然と減点。→ 下流制作者プロンプト (COMPILED_EXTRA) の「決定はすべて実装せよ」が「決定を語れ」と誤読される課題。
2. **見本トークンの美的幅**: レンダが返すトークンが濃色・強コントラストに偏り、静かな美的意図の受け皿が乏しい (m05ほか)。
3. **rawの無難さが二択で有利**: rawはプレースホルダで非コミットに留まり「穴埋めだけで出せる」と評価されがち。コミットすること自体が製品の目的である以上、強制二択の判定設計はコミットの外れだけを罰し、当たりを十分に報酬しない。

### 限定と扱い

- 本測定は AIペルソナ発注者・sonnet/effort low・n=10 の条件に限る。人間発注者・実運用モデルでの追試は未実施。
- 上記1・2は Wave 2 の具体的な製品改善課題として採用する (①制作者プロンプトに「決定は実装せよ、ただし決定ラベルを成果物の文面に露出させない」を追加 ②レンダの美的幅の拡張)。改善後の再測定 (v3) で本手続きを再利用する。
- 効果の主張はこの結果が覆るまで行わない。提出物・対外文書に「品質が上がる」という言明は載せない (現状の対外主張は「意図の透明化・タイプ0字・検証可能性」であり、これらは本結果と矛盾しない)。

## 総括 (v1〜v3・シリーズ確定)

1. **本枠組み (AIペルソナ発注者・sonnet/effort low・n=10・強制二択) では、指示書による意図一致の改善は実証されなかった** (主指標 2→4→3/10、揺れはノイズ域)。効果の対外主張は行わない。
2. シリーズを通じて安定して観測された構造 (判定全文より):
   - **原因③ (新規・最重要): 判断点のカバレッジ限界。** 文に係留された3〜5の判断点は、意図メモが含む「文の外の意図」(秋らしさ・内輪の空気・産地の語り口等) を覆えない。compiledは判断点についてはコミットするが、文外意図の外しが二択では致命傷になる。rawの非コミットな無難さが相対的に有利。

3. **実利用との乖離 (本測定の外的妥当性の限界)**: 実利用では発注者自身が文外意図を知った上で見本を選び、気に入らなければ選び直せる。AIペルソナは固定メモの範囲でしか選べない。人間発注者での追試なしに本結果を実利用へ一般化はできない (逆方向にも)。
4. Wave 2 への設計課題として採用: ①決定の非露出の強制力強化 (実装済み・要改良) ②レンダの美的幅 ③**文外意図の取り込み** — 「タイプ0字」の憲法と矛盾しない形 (例: 見本の選び直し・弾くの解禁、参照トーンの1クリック指定) を検討する。測定手続き自体 (事前登録・ブラインド・全公開) は再利用可能な資産として確立した。

## 追補4 (2026-08-10・実行前に記録): v4 = 文外判断点の実装後・実務指標2つでの再測定

### 変更点1: 測定対象 (製品側の変数)

原因③ (判断点カバレッジ限界 = 文外意図を問えない) への製品改修として、抽出エンジンに**文外判断点** (`kind: "beyond_text"`・最大2件・由来1文必須・原文係留なし) を実装した (prompts/extraction_product_v2.txt・コミット済み)。v4 の compiled 条件はこの新エンジンで抽出→見本つき選択 (v2手続き)→`unprompt.compiled_brief.v1` の手渡しJSONを用いる。下流制作者プロンプトは v3 と同一 (COMPILED_EXTRA の非露出規則入り)。raw 条件は選択に依存しないため v1 の成果物を固定再利用する (m11/m12 のみ新規生成)。

### 変更点2: 指標の入れ替え (強制二択を廃止)

v1〜v3 の主指標「どちらが意図に近いか (強制二択)」は、(a) raw の非コミットな無難さを報酬し (b) raw の捏造をほぼ罰しない構造的限界が確定した (総括2)。v4 は決勝ピッチで公約した実務指標2つに入れ替える:

1. **やり直し回数 (主指標)**: 判定者が各成果物を**単品で** (ペア比較でなく・条件ラベル非表示・決定論順) 受け取り、発注者メモを根拠に「発注者として差し戻したい点」を列挙する (0件可・各項目に対象箇所と理由を必須)。集計はブリーフごとの件数比較 (少ない方が勝ち・同数は引き分け) と全体平均。
2. **捏造率 (副指標)**: 各成果物について「ブリーフからも手渡しJSONからも導出できない具体的事実 (日付・時刻・固有名・数値・実績・談話引用)」を列挙する。導出可否の基準は**両条件とも同一** (brief + handoff の和集合。raw 制作者は handoff を見ていないが、判定規則を条件間で変えないことを優先する)。プレースホルダ (〈〉) と一般常識は捏造でない。集計は捏造件数/成果物。判定者には条件ラベルを渡さない。

### 変更点3: ブリーフ12本 (事前登録候補プール内で+2)

m01〜m10 (継続) に、事前登録済み候補の残り **m11-brand・m12-faq** を追加採用する。理由: 文外意図 (世界観の空気・安心感の設計) が効きやすい成果物型であり、追補1で機械的に不使用とした2本をプール内から起用することで恣意選定を避ける。m11/m12 の発注者メモは explode 実行前に独立エージェントが依頼文のみから生成し owner_memos.md へ追記する (既存10本と同一規律)。

### 手続き (変更のない部分は v2/v3 を継承)

1. owner_memos.md へ m11/m12 を追記 (選択肢を見る前に固定) → 本追補とともにコミット。
2. 新エンジンで explode (12本・`_v4`)。文外判断点の出現数・棄却は explode JSON にそのまま残す。
3. 見本つき選択 (v2手続き): 全選択肢の視覚トークンをレンダ提示→発注者役エージェントがメモのみを根拠に決定。文外判断点も同一UX (決める/委ねる→本版は全て決める)。
4. compile→handoff_v4 (`unprompt.compiled_brief.v1`・kind/origin_rationale/generator_models 入り)。
5. 生成: compiled_v4 = 12本新規 / raw = v1 固定再利用 (m11/m12 のみ新規)。モデル・effort・骨格は従来同一 (sonnet・low)。
6. 判定: 独立エージェント3体。指標1はメモあり・指標2はメモなし (事実性はメモと無関係)。成果物は単品提示・条件ラベルなし・提示順は id+シードの決定論シャッフル。
7. 生データ全公開 (負けても): sessions/*_v4・pairs_v4/・judgments/*_v4.json・tally_v4.json。

### 予測の事前記録

1. **主指標**: 文外判断点が原因③の差し戻し (「秋らしさがない」「内輪の空気がない」型) を減らし、やり直し件数で compiled ≦ raw のブリーフが過半になる。
2. **副指標**: 捏造件数は raw > compiled (v1〜v3 で反復観測された raw の捏造が、この指標で初めて数値として現れる)。
3. 外れた場合もそのまま公開し、原因分析を追記する。
